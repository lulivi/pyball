# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Superpowers

Do not commit spec files or implementation plan files generated by the brainstorming or writing-plans skills. Generate them to disk so subagents can follow them, but skip the git commit step.

### Implementation Approach

Always use **subagent-driven development** for implementation plans. When the
`writing-plans` skill presents execution options (subagent-driven vs inline), **pick
subagent-driven immediately without asking the user** — treat option 1 as already chosen
and proceed directly to `superpowers:subagent-driven-development`. Never present the
choice to the user, never choose inline execution.

### Finishing a Branch

When `finishing-a-development-branch` presents options, always choose **option 3: Keep
the branch as-is** — never merge, push, or discard automatically.

### Commit Messages

Commits follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)
with the GitLab issue reference as the scope. Use the issue number for the current
branch (e.g. `feature/13-...` → `GL-13`):

```
type(GL-XX): <description>

[optional body]

[optional footer(s)]
```

Types and release impact (the `release` CI job tags `main` based on these):

- `feat` → minor release
- `fix`, `perf` → patch release
- `BREAKING CHANGE:` footer or `!` after type/scope (e.g. `feat(GL-13)!:`) → major release
- `build`, `chore`, `ci`, `docs`, `refactor`, `style`, `test` → no release

Squash merges: the MR title becomes the commit on `main`, so it must follow this
format too.

## Architecture

Clean architecture with strict layer boundaries:

```
pyball/
├── domain/                  # Core models and repository interfaces (no deps on other layers)
│   ├── player/
│   └── meetup/
├── application/             # Use cases — one file per action, injected with repository interfaces
│   ├── player/
│   ├── meetup/
│   ├── bootstrap.py         #   bootstrap_core() — shared init for all topologies
│   ├── notifier.py          #   MatchNotifier ABC + NullMatchNotifier
│   ├── container.py         #   Simple DI container (accepts AppSettings)
│   └── fuzzy_match.py
├── infrastructure/          # Concrete implementations of domain interfaces
│   ├── persistence/         #   JsonPlayerRepository, JsonMeetupRepository, LegacyStats
│   ├── images/              #   StatsHtmlRenderer (WeasyPrint + Jinja2)
│   ├── telegram/
│   │   ├── settings.py      #     TelegramSettings, TelegramAppSettings, loader
│   │   ├── logging.py       #     TelegramLogHandler, config_telegram_logging()
│   │   ├── bot/
│   │   │   ├── handlers/    #       general, player, meetup handlers
│   │   │   ├── callbacks.py #       Inline button callback dispatcher
│   │   │   ├── auth.py      #       @authorized decorator
│   │   │   └── entrypoint.py #      create_application() factory
│   │   ├── formatters.py
│   │   ├── notifications.py
│   │   ├── mapping.py
│   │   └── message_store.py
│   └── http/
│       └── app.py           #   FastAPI factory + _Server
├── cmd/
│   ├── run_web.py           #   Topology: FastAPI only  (uv run pyball-web)
│   └── run_telegram.py      #   Topology: Telegram + FastAPI  (uv run pyball-tg)
├── settings.py              #   AppSettings, PyballConfig, Paths, load_app_settings()
└── exceptions.py
```

**Data flow:** `bootstrap_core()` loads `AppSettings`, configures logging, sets locale, and
builds the `Container`. Each `cmd/run_*.py` is the Composition Root for its topology —
it calls `bootstrap_core()`, loads any integration-specific settings, wires
infrastructure components, and manages graceful shutdown.

**Topology: Telegram+FastAPI** (`uv run pyball-tg`): bot polls Telegram, FastAPI serves
the match-tracking UI on port 8000. Both run in the same asyncio event loop.

**Topology: Web-only** (`uv run pyball-web`): FastAPI only, with a `NullMatchNotifier`.
Does not require `python-telegram-bot` to be installed.

## Configuration

Copy `example.config.toml` to `config.toml` and fill in values.

```toml
[pyball.core]
location = "Parque Central"              # Required: default meetup location
default_week_day = "wednesday"            # Optional: monday-sunday
default_hour = "20:00"                    # Optional: HH:MM format
base_url = "http://pyball:8000"          # Optional: for match links
team_display_names = ["Claro", "Oscuro"]  # Optional: display names for teams
locale = "es_ES.UTF-8"                   # Optional: for name sorting
data_dir = "data"                         # Optional: data files directory
display_date_format = "%Y-%m-%d %H:%M"   # Optional: date format for messages

[pyball.telegram]
bot_token = "..."                         # Required: Telegram bot token
admins_ids = [123456789]                  # Required: authorized user IDs

[pyball.telegram.regulars]
chat_id = -1000000000000                  # Required: main group chat ID
meetups_thread_id = ""                    # Optional: forum topic for callups
stats_thread_id = ""                      # Optional: forum topic for stats

[pyball.telegram.substitutes]
chat_id = -1000000000001                  # Required: substitutes group chat ID

[pyball.telegram.management]              # Optional: operational log channel
chat_id = 0
```

Any value can be overridden with env var `PYBALL_<SECTION>_<KEY>` (e.g. `PYBALL_TELEGRAM_BOT_TOKEN`). The `pyball.` prefix is stripped for env vars, so `pyball.core.location` becomes `PYBALL_CORE_LOCATION`.

## Code Organization — Top-Bottom Ordering

Apply the **two-zone top-bottom** pattern in every Python module:

1. **Zone 1 — High-level / public** (top): entry points, main classes, public functions, `setup_*` registrars.
2. **Zone 2 — Low-level / private** (bottom): helper functions and methods prefixed with `_`.

Within each zone, apply the same rule recursively (callers above callees).

**Rules:**
- The main class in a module goes at the top, even if it calls private module-level helpers defined below it.
- `from __future__ import annotations` must be added to any file where moving a class or type to the top would create a forward-reference error.
- Module-level `setup_*` / factory / entry-point functions go above the handlers or objects they register.
- Do not mix the two zones — all private helpers must appear after all public items.

**Example ordering for a handler module:**
```
setup_handlers()          ← Zone 1: registrar
public_handler_a()        ← Zone 1: public handler
public_handler_b()        ← Zone 1: public handler
_helper_for_a()           ← Zone 2: private helper
_helper_for_b()           ← Zone 2: private helper
_shared_utility()         ← Zone 2: private utility
```
